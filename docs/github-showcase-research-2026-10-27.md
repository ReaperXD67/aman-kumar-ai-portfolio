# GitHub project showcase research

Source review: 2026-10-27. Scope: replace the plain flagship-project bodies with original, animated engineering showcases. These are concrete implementation references, not a claim that any profile can be ranked objectively as the best on the internet. No downloaded source was executed and no new runtime dependency is required.

## What the current profile is missing

The profile already has an animated hero and contribution assets. Its three flagship bodies still repeat a stack line, CI badge, paragraph, decision sentence and links; the architecture atlas is hidden in a closed disclosure. The largest improvement is therefore a prominent visual for **each project**, directly above its short explanation.

Use a real interface capture as the main plane, then reveal a short, source-grounded system path and one failure boundary. Give Agent, AtlasLM and KarixMC different compositions. Keep their live/source links in ordinary Markdown underneath so the evidence remains usable when images do not load.

## Recommended three-showcase sequence

1. **Autonomous Personal Agent:** an authored control-plane blueprint because the project is a local alpha. A request reaches approval, a leased worker owns the task, then a late completion is refused before the recorded receipt. Show the ownership boundary, not fictional production telemetry.
2. **AtlasLM:** begin with its real document workbench. Dense and lexical routes split and fuse into selected evidence; an insufficient-evidence branch visibly stops before generation. End on citations and a source pointer. Do not depict every query as successful.
3. **MinePulse / KarixMC:** begin with its real storefront. Peel to the Paper-plugin boundary, signed batch, claim/acknowledgement and ledger; briefly illuminate expiry/refund as the recovery branch. A dark, spatial diagram can distinguish this from AtlasLM's document composition.

For each: one large linked visual, one concise engineering decision, direct live/source links, then optional deeper detail. Avoid three repeated mini-dashboard templates and an extra badge wall.

## GitHub delivery constraints

- README HTML is sanitized: scripts, inline styles and class/id attributes are removed. The image is the authored surface; README markup provides accessible labels, links and disclosures. [GitHub's rendering pipeline](https://github.com/github/markup#github-markup)
- In SVG image context, JavaScript is disabled and external images/styles cannot be loaded; inline data URLs can be used. Embed owned captures as raster data inside SVG or composite them into APNG/GIF frames. Use pure SVG primitives for routes; avoid external fonts and `foreignObject`. A browser render of the standalone SVG is not enough—verify the actual GitHub image. [MDN SVG image restrictions](https://developer.mozilla.org/en-US/docs/Web/SVG/Guides/SVG_as_an_image#restrictions)
- Commit original assets and their generator to the profile repository with versioned filenames. Do not depend on another maintainer's demo host, a rate-limited image API, expiring attachment URL or authenticated endpoint. Give automated generation only the permissions it needs and pin action revisions.
- Supply separate desktop and mobile compositions through `picture`, with a static reduced-motion source first. Mobile must enlarge the meaningful nodes and crop/reflow the capture, rather than shrinking a 1200px diagram. Keep key text as real Markdown as well as inside the graphic.
- Give the animation a meaningful first frame and restrained timing. Provide a visible static-view link and collapsible motion where useful. APNG/GIF has no native pause control, so do not promise a pause button embedded in the image. Validate the actual profile at narrow width, light/dark mode and reduced motion.
